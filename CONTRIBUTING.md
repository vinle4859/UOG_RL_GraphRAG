# Contributing Guide

Guidelines for the team to collaborate effectively on this project.

---

## Quick Start

```bash
# 1. Clone & setup
git clone <repo-url> && cd UOG_RL_GraphRAG
python -m venv .venv && .venv\Scripts\activate
pip install -e ".[dev,notebooks]"

# 2. Install hooks
pre-commit install

# 3. Create a branch
git checkout -b feature/my-feature

# 4. Code, test, commit
pytest
git add . && git commit -m "feat: add my feature"
git push origin feature/my-feature

# 5. Open a Pull Request on GitHub
```

---

## Branch Strategy

| Branch | Purpose |
|--------|---------|
| `main` | Stable, tested code. **Never push directly.** |
| `feature/<name>` | New features (e.g., `feature/faiss-vectorstore`) |
| `fix/<name>` | Bug fixes |
| `experiment/<name>` | Exploratory work, notebooks (e.g., `experiment/title-clustering`) |
| `data/<name>` | Data pipeline changes |

### Naming Conventions

- Use lowercase with hyphens: `feature/graph-retrieval`
- Include your initials if helpful: `feature/jd-community-summary`

---

## Commit Messages

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>: <short description>

[optional body]
```

**Types**: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `experiment`

**Examples**:
```
feat: add FAISS vector store backend
fix: handle empty document list in chunker
docs: update README with benchmark results
test: add unit tests for retrieval metrics
experiment: try HDBSCAN for paper clustering
```

## Code Style

- **Ruff** handles linting and formatting (configured in `pyproject.toml`).
- Pre-commit hooks run automatically on `git commit`.
- To manually check: `ruff check . && ruff format --check .`
- To auto-fix: `ruff check --fix . && ruff format .`

### Key conventions

- Type hints on all public function signatures.
- Docstrings (NumPy style) on all public classes and functions.
- Module-level docstring explaining purpose at the top of every file.
- Constants in `UPPER_SNAKE_CASE`, classes in `PascalCase`, functions/variables in `snake_case`.

## Testing

```bash
# Run all tests
pytest

# Run with coverage
pytest --cov=src

# Run a specific test file
pytest tests/test_metrics.py
```

- Add tests for any new public function.
- Tests go in `tests/` mirroring the `src/` structure.
- Use fixtures from `tests/conftest.py` for shared test data.

---

## Pull Request Checklist

Before requesting review:

- [ ] Code follows the style guide (ruff passes)
- [ ] Added/updated tests for changed code
- [ ] All tests pass (`pytest`)
- [ ] Updated docstrings/comments
- [ ] Updated README if user-facing behaviour changed
- [ ] No secrets or API keys in the code

## Working with Data

- **Raw papers** (`data/raw/`): Provided by the extraction engineer. **Do not modify.**
- **Processed data** (`data/processed/`): Generated by our pipeline. Gitignored.
- **Embeddings** (`data/embeddings/`): Vector store files. Gitignored.
- **Graphs** (`data/graphs/`): Serialised knowledge graphs. Gitignored.

If you need to share processed data artifacts, upload them to a shared drive and reference the URL in the PR description.

---

## Environment Variables

- Copy `.env.example` to `.env` and fill in your values.
- **Never commit `.env`** — it's in `.gitignore`.
- If you add a new env var, also add it to `.env.example` with a descriptive comment.

---

## Notebooks

- Keep notebooks in `notebooks/`.
- Clear outputs before committing (to keep diffs clean).
- Number notebooks to indicate workflow order: `01_`, `02_`, etc.
- Notebooks are for **exploration**; production code belongs in `src/`.
